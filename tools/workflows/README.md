# 文档流水线（dynamic-workflows）

这两个脚本是**改文档时用的流水线**：盘点 → 差距分析 → 中英文重写 → 三个独立复核
（新读者 ×2 + 事实核对 ×1）→ 两轮修订 → 机械闸门 → 仓库总闸门 → 提交 → 交付。

| 脚本 | 干什么 |
|---|---|
| `readme-refresh.dwf.ts` | 整条流水线（从盘点跑到提交） |
| `readme-refresh-finish.dwf.ts` | 收尾版：盘点与重写已经落地时，只做「补完没改完的意见 → 跑两道闸门 → 提交 → 交付」 |

## 怎么跑

用 `dynamic-workflows` 这个技能在**仓库根目录**跑（脚本里的路径都是仓库相对路径）。
中间产物落在 `.temp/readme-survey/`（gitignored）—— 盘点清单、差距清单、
三份复核意见都在那儿。

```bash
# 机械闸门单独跑（秒级，提交前随手跑）
node tools/check-readme.mjs
```

## 这一版修掉的东西（别改回去）

这些都是上一轮真踩过的坑，脚本头部的注释里也写了同样的内容：

1. **长任务要给足超时，并且把超时变成数据而不是异常。**
   上一轮 `world.run("bash", ["verify.sh"])` 撞 40 分钟超时 → 整个脚本 errored →
   后面「提交、交付」两个阶段根本没跑到：**文档写完了却没人发布**。
   现在给 90 分钟，并用 `try/catch` 包住 —— 超时记成「超时，没拿到结果」，
   流程照样走到提交与交付。

2. **闸门的输出必须进报告。**
   上一版把 `world.run` 的 stdout 存进变量却没写进返回报告，闸门失败时只能去翻
   `web/test-results/run-*/.last-run.json` 与 `error-context.md` 才找得到原因。
   现在 gate 的 stdout 出现在 `notCovered`、`findings` 的 evidence 与交付说明里。

3. **耗时要按实测说。**
   `bash verify.sh` 在空机器上约 **10 分钟**（e2e 那一段约 4 分钟）——
   别按「25~30 分钟」估，估错了会白等。

4. **盘点代理要设预算。**
   上一轮五个盘点代理各读几万行代码，整轮烧掉 **57M tokens**
   （事实核对员单跑 11M、修订编辑两轮 13.6M），而修订产物的绝大部分价值在那两轮修订里。
   现在：
   - 盘点清单比源码新就**复用**（不重新盘点）；
   - 盘点目标从五个收到三个，每个都有明确的**阅读预算**（多少文件、多少行、不要通读什么）；
   - 事实核对员最多核 **20 条**断言，而不是把文档里的每句话都去代码里对一遍。

## 机械可判的部分不在流水线里

链接、命令、路径、配置默认值、端点、闸门步数、SDK 版本 —— 这些由
[`tools/check-readme.mjs`](../check-readme.mjs) 判（`verify.sh` 的第一步，CI 里也有一个 job）。
流水线里的代理只负责**语义层面**的判断（读者视角、事实核对）。
